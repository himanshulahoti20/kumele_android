# Kumele — Coding Rules & Bug-Fix Workflow

Read docs 01–03 first. This file is the standing checklist for any change in this repo.

## Hard rules

- **Never change pre-existing architecture or UI — whatever's already there — unless the user explicitly asks for that change.** This applies broadly, not just to the examples below: no new DI container, no repository layer, no Combine-publisher rewrite of the async/await services, no coordinator/router pattern to replace the `AppState.currentScreen` switch or the `TabViewModel` flag-driven overlays, no restructuring a View's layout/styling while fixing its data wiring. A task being about API integration, a bug fix, or "cleanup" is not implicit permission to also refactor, rename, or redesign something adjacent. If the existing pattern seems suboptimal, that's a conversation to have with the user first — not a unilateral change bundled into an unrelated task.
- **Never touch the mobile (iPhone/iPad) UI/UX** — layout, fonts, colors, spacing, SwiftUI view structure — without being explicitly asked to. Per `HANDOFF.md`, this UI is the accepted canonical design. Backend/API wiring should not visibly change how a screen looks or behaves beyond replacing mock data with real data (a corrected/relabeled form field, e.g. fixing a wrong placeholder string, is a content fix, not a UI redesign, and is fine when it's part of fixing the bug at hand).
- **Never rename or move files/folders** unless the task explicitly requires it (e.g. adding a genuinely new feature area's `Services`/`ViewModels` folder). The existing `Views/Common` / `Views/iPhone` / `Views/iPad` / `Views/Components` structure and the `_iPhone`/`_iPad` naming convention are load-bearing — other code and possibly build settings may depend on paths.
- **Never introduce a second networking or HTTP client.** `Kumele/Networking/{APIClient,APIEndpoint}.swift` (actor-based, Keychain-backed, Bearer JWT, auto-refresh) is the current, real stack — see [05_ImplementedAPIs.md](05_ImplementedAPIs.md) §0. `NetworkManager`/`NetworkManagerProtocol`/`APIResponse<T>`-as-envelope and `Alamofire`/`NetworkService.swift` are both dead code from an earlier iteration — do not resurrect either or treat them as precedent.
- **Session storage is already Keychain-backed** (`KeychainTokenStore`, via `APIClient`) — the old "known gap, don't fix as a side effect" caveat that used to live here no longer applies; that rework already happened. Don't reintroduce a plaintext-token storage path as a "simplification."
- **Reuse existing services, models, and ViewModels before creating new ones.** Before adding a new `Codable` model, check `Kumele/Models/` for one that already covers the shape (especially `User`, `EventModel`, `BlogModel`, `PaginatedResponse`). Before adding a new service, check whether an existing one under `Kumele/Services/{Auth,Blog,Event,Chat,Notifications,API}/` already exposes (or is one method away from exposing) what you need — see doc 05 for the current inventory, including which correctly-coded services have zero callers and just need wiring rather than a new implementation.
- **Every endpoint path lives in `Kumele/Core/APIConstants.swift`, never as an inline literal.** All ~150 endpoints the app calls are registered there as `[String]` path-segment constants (fixed paths as `static let`, parameterized ones as `static func(...) -> [String]`), organized by feature area (`APIConstants.Auth`, `.Events`, `.Blog`, etc.) matching the `Service` groupings. When adding a new endpoint call, add its constant to `APIConstants` first, then reference it from the `Service` — never write `path: ["some", "literal"]` directly in a `Service` file. This is a hard rule going forward, not just how the existing ones happened to get organized.
- **"Check/go through section X" means a full audit-and-implement cycle, not just a report.** When asked to check or go through a particular API section (Auth, Hobbies, Events, Users, Payments, Content, etc.): audit every endpoint's implementation/wiring status, then for every "dead code" endpoint (correct client method, zero UI callers) check whether real UI already exists for it (a screen/button/field with hardcoded, dummy, or missing data). Wire up every one that has genuine existing UI — this is pre-authorized, don't stop to ask first, it's a carve-out from the "never touch UI unless asked" rule above since asking for the section audit already covers it. Leave alone every one with no existing UI at all — don't design or build new screens for it, just flag it clearly with why. While at it, also check for the "silently dropped/mismatched field" bug class — a `Codable` model that doesn't declare a field the backend actually sends, or maps to the wrong JSON key — since this is invisible to endpoint-wiring checks alone (the call still succeeds, it just quietly returns `nil`/wrong values forever). Real examples found this way: `EventModel.endTime` (backend sends `ends_at`, model only recognized `endsAt`/`end_time`), `AuthTokens` (missing `email`/`role`/`emailVerified` despite being `required` in the schema), `User` (missing `profileCompleteness` entirely).
- **A section audit covers every target that ships the app, not just iPhone/iPad.** The project has 5 targets — `Kumele` (iPhone/iPad), `Kumele TV`, and `Kumele Watch App` (see doc 01 §1/§7/§8) — and "check section X" means checking that section's UI across all of them, not just the phone/tablet views. Concretely: `Kumele TV` shares the real `Networking`/`Services`/most `ViewModels`/`Models` files with the main target (multi-target membership in the synchronized group, see `project.pbxproj`'s `PBXFileSystemSynchronizedBuildFileExceptionSet` for the exact file list) — its own `Kumele TV/View/*` screens can be dead-code/hardcoded on top of already-live plumbing exactly like an iOS screen would be, so audit and wire them the same way. `Kumele Watch App` is fully isolated — no `Networking`/`Services`/`ViewModels` folder, zero shared files, no `WatchConnectivity` — every screen renders hardcoded sample data and login is a fake timer. Treat Watch API work as starting from zero, and because wiring it up at all is an architecture decision (talk to the backend directly vs. relay through the phone app via `WCSession` — neither exists today), surface that choice to the user before building rather than picking one unilaterally.
- **No comments that read as AI-generated.** No restating what the code obviously does ("// loop through users and check email"), no comments narrating the current task/fix/PR ("// fixed per user request", "// added for the login bug", "// TODO: implement this later" left behind after actually implementing it), no comment templates/boilerplate headers beyond what the file already has. A comment is only earned by a genuinely non-obvious WHY — a backend quirk being worked around, an ordering constraint, a subtlety a future reader would otherwise trip over. If deleting the comment wouldn't cost a future reader anything, don't write it.

## Naming & structure conventions to follow

- Services: `Kumele/Services/<Area>/<Area>Service(s).swift` (+ a `<Area>Service(s)Protocol.swift` where a protocol seam is actually needed, e.g. for testability — plenty of current services are a concrete `final class` with no protocol, that's fine too), constructor injects `client: APIClient = .shared`, one method per endpoint using `client.send(APIEndpoint(...))`.
- ViewModels: `Kumele/ViewModels/<Area>ViewModel.swift`, `ObservableObject`, constructor injects the service protocol with a concrete default, `@Published` state + `@Published var xError: String?` (matches `errorBlog`, `eventsListError`, etc. naming already in use).
- Views: idiom-split via `Views/Common/<Area>/XView.swift` (router) → `Views/iPhone/<Area>/XView_iPhone.swift` / `Views/iPad/<Area>/XView_iPad.swift`.
- Models: `Codable` struct, `CodingKeys` mapping API `snake_case` to Swift `camelCase`, optional-heavy for defensive decoding, matching the style already in `User.swift`/`EventModel.swift`/`BlogModel.swift`.
- Error surfacing: `Views/Components/ErrorPageView.swift` with a `retryAction` closure — don't invent a new error-display component for a new feature area.

## Bug-fix workflow

1. **Identify root cause** before touching code. Given how much of this codebase is intentionally mocked (see doc 02), "broken" often means "never wired up" rather than "wired up incorrectly" — confirm which one you're looking at first (check for a commented-out real call in the relevant Service).
2. **Explain the root cause** (to the user, briefly) before implementing a fix, especially if the fix touches shared code (anything under `Kumele/` that's also compiled into the `Kumele TV` target — see doc 01 §1's shared-file list).
3. **Implement the minimal fix.** Don't use a bug fix as cover to also clean up adjacent code, rename things, or add abstractions.
4. **Verify the fix** against the actual failure mode, not just "it compiles" — for API work this means an actual network round-trip against the real backend (see doc 03), not just simulator UI looking right with mock data still active.
5. **Check for side effects**, especially:
   - Shared-file changes affecting both iOS and TV (doc 01 §1).
   - `TabViewModel` flag changes — it's a single large shared object; adding/renaming a `@Published` property can collide with an existing one or affect an unrelated screen that also reads `TabViewModel`.
   - Model changes — `EventModel`/`User`/`BlogModel` are used across many views; adding a required (non-optional) field or renaming a `CodingKey` can break decoding for every consumer, including the `Kumele TV` target since the file is shared.

## After every API implementation: how-to-verify steps

Every time an API call is implemented or changed (new endpoint wired up, a bug fix to an existing call, a request/response shape correction), end the response with concrete steps for checking it inside the running app — not just "it should work now." At minimum:

1. **Where to trigger it**: which screen, which button/action, and any state it requires first (logged in? a specific field filled? a specific prior step completed?).
2. **What to watch for**: the exact `➡️ [API]` / `⬅️ [API]` console lines to expect (method, path, and — for the interesting cases — what the payload/response should contain), per the request/response logging in `APIClient` (see doc 05 §0). Call out the specific status code and any distinguishing response field, not just "200 OK."
3. **What "working" looks like in the UI**, if the call drives visible state (a screen populating, an error banner appearing, navigation happening) — and what a failure looks like too, if that's relevant (e.g. an inline error message rather than nothing happening).

Keep this tight — a short numbered list, not a full manual test plan — but don't skip it. The goal is that the user can confirm a fix actually works against the real backend in under a minute, without having to ask "so how do I check this."

## Async/await, not Combine

All service/network code is `async throws`, called via `await` inside `Task { }` blocks from views/ViewModels (no `@Published` pipelines wired through Combine operators for network results). Match this — don't introduce `AnyPublisher`/`Combine` chains for new async work.

## When existing code conflicts with "best practice"

Most of the original known gaps this section used to list (no Keychain, no token refresh, a dead Alamofire stack) have since been fixed by the networking rework — see [05_ImplementedAPIs.md](05_ImplementedAPIs.md) for the current, accurate list of what's still genuinely missing, wrong, or dead code with no caller. New gaps will keep surfacing as the app is used more (that's the point of doc 05's "runtime-verified" section). The rule stands regardless of which gaps are currently open: do not silently "fix" something you notice while doing unrelated work — flag it and let the user decide priority and scope, per the standing instruction to keep changes minimal and scoped to what was actually asked.
